# 計算負荷と性能検証

## 標準動作

- 定常計算の表示更新は最大4回/秒。前の表示の処理完了を確認してから送信します。
- Workerは約50 msの計算区間ごとに操作を受け付ける機会を設けます。1ステップ自体が長い場合は、その終了後になります。描画スレッドとは別なので、画面のフレーム間隔に合わせて細かく待機することはしません。
- 初回表示の直後だけ16 ms待機し、短い計算でも開始直後の停止操作を受け付ける機会を確保します。
- 表示用の配列だけFloat32に変換し、Transferableとして送信します。変化しない水深は途中の更新に含めません。
- ROMS内部、終了場、停止場、保存結果、追加実験の開始場は従来のFloat64を維持します。
- 配列取り出し時のWASM作業メモリは、各配列ごとではなく1回の取り出し全体で共用します。
- 直近48時間の全地点履歴は維持します。固定水深は1つの配列を共有し、履歴専用のFloat32配列は再コピーせず所有します。履歴予算64 MiBには共有水深も含みます。
- 追加実験の途中表示・保存用追加RUNの進捗も実時間基準で更新します。粒子の保存間隔や保存結果の精度は変えません。

画面用に単精度へ丸めた値を、モデルの次ステップや追加実験の開始条件へ戻すことはありません。カラーバーの自動範囲は計算中の表示用配列から求めるため、終了場の表示とは最下位桁が異なる場合があります。

## 計測

終了・停止のWorkerメッセージの `performance` に `stepsMs`、`snapshotMs`、`snapshots`、`updates`、`wallMs` を含めます。時間の単位はmsです。`stepsMs` はROMSの時間積分呼び出し、`snapshotMs` は状態配列の取り出しです。`wallMs` は時間積分ループ全体で、起動・初期化・画面側描画は含みません。これらは計測用情報で、実験条件を変更しません。

`tests/browser/runtime-performance.spec.js` はGit HEADの旧Workerと現在のWorkerを同じブラウザーで動かし、転送量、更新回数、起動を含む経過時間、終了場を比較します。HEADにも改善が入っている場合は旧版との比較を省略し、現行版の数値・転送型を検査します。旧版はGitの状態に依存するため、固定された長期ベンチマークではありません。結果は `.tools/performance/worker-comparison.json` に出力します。

## WASM最適化の試験

同梱WASMを上書きせず、Binaryenの追加O3最適化を別ファイルへ適用して比較します。これはFortran全体のO3再コンパイルやSIMD化とは別の試験です。高速化が確認できない候補は標準採用しません。fast-mathや計算の単精度化は使用しません。

候補ファイル作成後に `node scripts/benchmark-kernel.mjs <候補.wasm>` を実行します。物理モデルの32×32×3、300ステップを対象に、1回のウォームアップ後、候補・標準の順番を交互にして3回ずつ計測します。終了場の差も検査し、`.tools/performance/kernel-comparison.json` に出力します。ほかの負荷の高い処理を止めて実行してください。1条件の結果を全海域・全端末・全モデルに一般化しないでください。

## 試験記録（2026-10-17）

Windows上のChrome、物理モデル、24×24×3、200ステップの1条件では次の値でした。描画負荷を加えず、受信すると直ちにACKするWorker比較です。実アプリ全体の速度保証ではありません。

| 指標 | 改善前 | 改善後 |
| --- | ---: | ---: |
| 起動を含む経過時間 | 3.628秒 | 3.218秒 |
| 途中表示の更新数 | 37回 | 9回 |
| 途中表示の配列転送量 | 3,694,080 bytes | 428,544 bytes |

同じブラウザーの新旧Worker間で終了場は完全一致しました。Nodeの基準実行との差は最大約2.5e-18でした。別途、ネイティブ参照の物理・生物・GLS各ケースとの照合も通過しました。

Binaryen 129による追加O3最適化では、物理WASMが4,159,501から3,469,723 bytesに縮小し、試験終了場の差は0でした。一方、計算速度比は試行によって約0.94〜1.03倍と安定せず、配布するWASMは置き換えていません。FortranのO3/SIMD再コンパイルは今回の試験には含めていません。
